# badcase 分类体系与归因

版本：v1.0（2026-11-18）　用途：统一团队对 badcase 的命名、归因与预防口径，避免「每个人都有自己的叫法」。

## 归因三问

处理任何 badcase 先回答：**模型能力问题、数据问题，还是规范问题？** 三者对应不同处置：模型问题进训练反馈，数据问题返修数据，规范问题改 SOP。归因错误比 badcase 本身更浪费成本。

## 分类树

```text
badcase
├── 1. 事实性
│   ├── 1.1 编造数据/文献/规则
│   ├── 1.2 名称与归属过时（机构更名、区划调整）
│   └── 1.3 张冠李戴（同名混淆）
├── 2. 指令遵循
│   ├── 2.1 硬性要求未达（字数/格式/要点数）
│   └── 2.2 隐含要求未达（场景适配、语域）
├── 3. 逻辑
│   ├── 3.1 前后矛盾
│   └── 3.2 结论与论据脱节
├── 4. 安全
│   ├── 4.1 拒答不足（有害请求给了方法）
│   └── 4.2 过度拒答（无害请求被拒）
├── 5. 多轮
│   ├── 5.1 指代丢失
│   └── 5.2 状态污染（前轮确认信息被篡改）
└── 6. 数据侧（标注员侧）
    ├── 6.1 规范歧义导致的标注不一致
    └── 6.2 自检缺失（未按清单自检即提交）
```

## 各类案例与预防

### 1.1 编造数据
- **案例**：回答民宿行业问题时输出「2025 年行业报告显示均价上涨 23%」，无报告名、无出处。
- **归因**：模型问题为主；数据侧未给「无出处数字」的负例。
- **预防**：SFT 数据加入「声明局限＋给查询路径」的正例；评估量表把精确无出处数字锚定为 0 分。

### 1.2 名称过时
- **案例**：仍称「湖南省博物馆」（2022 年已更名湖南博物院）。
- **归因**：规范问题——规范里没有「官方名称以现行版本为准」的红线，团队口径不一。
- **预防**：写入 SFT 规范质量红线第 2 条；badcase 库沉淀「易过时实体清单」，定期核对。

### 2.1 硬性要求未达
- **案例**：要求「不超过 50 字」，回复 120 字。
- **归因**：模型问题；但若该类数据在 SFT 训练集中占比过低，属数据问题。
- **预防**：SFT 配比检查（字数受限任务 ≥ 10%）；评估样例把超字数锚定为指令遵循 1 分。

### 4.2 过度拒答
- **案例**：请写一首秋天短诗，回复「我无法进行文学创作」。
- **归因**：数据问题——安全类正例里「拒答」样本过强，泛化到无害请求。
- **预防**：SFT 数据中保持「安全拒答：无害创作」的配比平衡；badcase 按周统计拒答误伤率。

### 5.1 指代丢失
- **案例**：前轮聊安吉白茶，本轮问「它多少钱一斤」，模型回答龙井价格。
- **归因**：模型问题；多轮 SFT 数据中指代场景不足。
- **预防**：多轮数据必须含 ≥ 20% 指代/状态追踪场景（见 SFT 规范配比表）。

### 6.1 规范歧义
- **案例**：同一回复，A 标「略优」、B 标「相当」，复查发现两人对「风格差异是否参与判定」理解不同。
- **归因**：规范问题（不是标注员问题）。
- **预防**：偏好规范第 1 条明确「无关差异不参与判定」；双人 Kappa < 0.75 时首先排查规范歧义，其次才是个人偏差。

## 周转机制

badcase 按周归档：新案例 → 定级（阻塞/一般）→ 归因三问 → 进入对应处置队列 → 预防措施回写规范（变更走版本管理）。**每一条预防措施都要落到具体文件与条款**，不写「加强培训」这类不可验收的结论。
