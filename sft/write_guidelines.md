# SFT 数据编写规范

版本：v1.0（2026-11-18）　适用范围：SFT 指令数据、多轮对话数据的编写与自检。

## 1. 目标

产出「模型学什么」的第一手数据：指令清晰、回答可靠、格式一致、覆盖多样。SFT 数据的质量上限决定模型下限，规范的意义是把个人风格收敛为团队可复现的产出。

## 2. 任务类型配比（建议）

| 任务类型 | 配比 | 说明 |
|---|---|---|
| 开放问答 | 25% | 常识、知识类，重事实准确性 |
| 多轮对话 | 20% | 状态追踪、指代消解、需求澄清 |
| 文本创作与改写 | 20% | 应用文、文案、润色，重指令遵循 |
| 信息抽取与格式化 | 15% | 抽取、模板、表格化，重格式一致 |
| 生活服务与规划 | 15% | 行程、流程、比较决策，重实用 |
| 安全与边界 | 5% | 拒答边界、时效边界、医疗边界 |

配比按项目需求调整；单批数据内同一模板不得复用超过 2 次。

## 3. JSON 字段规范

```json
{"id":"sft-001","task_type":"开放问答","domain":"生活常识","difficulty":"易","messages":[{"role":"user","content":"…"},{"role":"assistant","content":"…"}],"quality_check":{"self_checked":true,"fact_check":"通过"}}
```

- `id`：`sft-` 前缀 + 三位序号，全库唯一，废弃数据只标记不删除。
- `task_type` / `domain` / `difficulty`：取值见上表与枚举表（易/中/难）。
- `messages`：user / assistant 交替，必须以 assistant 结尾；多轮需体现状态一致性。
- `quality_check`：自检字段，`fact_check` 取值 通过 / 已声明局限 / 存疑待核，存疑禁止提交。

## 4. 内容质量红线（违反任意一条即返修）

1. **事实性**：不确定的事实不编造；名称、数字、政策以官方口径为准；时效性内容必须声明局限。
2. **常识精准**：机构名、地名、规则用全称与现行版本（例：湖南省博物馆已于 2022 年更名为湖南博物院）。
3. **安全**：有害请求一律不提供方法，转为合法替代话题；医疗、法律只给通用信息与就医/咨询信号。
4. **多轮一致**：后轮不得丢失或篡改前轮已确认的信息（人名、日期、商品）。
5. **格式**：标点统一全角；数字用法统一；要求字数时严格遵守。

## 5. 多样性要求

- 同一领域连续不超过 5 条；难度分布约 4:5:1（易/中/难）。
- 用户画像多样：语气（口语/正式）、身份（学生/家长/从业者）、意图明确度（清晰/模糊）。
- 回答长度服从任务需要：明确要求字数时严格达标；无要求时宁短勿水。

## 6. 提交前自检清单

1. 指令是否自含（不看上下文也能理解）？
2. 回答是否全部满足指令的显式与隐式要求？
3. 事实类内容是否核过权威口径？不确定的是否已声明？
4. 多轮上下文指代是否一致？
5. 有无安全/隐私风险内容？
6. 标点、字数、格式是否符合第 4 条？
7. 是否与已有数据重复或高度同模板？
8. `quality_check` 字段是否如实填写？

## 7. 变更管理

- 本规范以版本号管理；字段增删、红线调整属于重大变更，需在项目群公告并重新试标（20 条，一致性达标后恢复正式标注）。
- 数据集版本与规范版本对齐：`dataset_v1.2` 表示按规范 v1.2 产出。
